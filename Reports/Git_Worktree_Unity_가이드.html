§1워크트리가 뭔지 1분 만에

보통 git은 저장소 1개 = 폴더 1개 = 한 번에 브랜치 1개만 체크아웃할 수 있다. 그래서 브랜치를 오가면 파일이 통째로 바뀌고, Unity는 그때마다 리임포트를 한다.

워크트리(worktree)는 "같은 저장소를 바라보는 추가 폴더"다. 커밋 역사(.git 데이터)는 하나를 공유하지만, 폴더마다 서로 다른 브랜치를 동시에 펼쳐둘 수 있다. 그래서 Claude Code 채팅 2개가 서로 파일을 덮어쓰지 않고 동시에 작업할 수 있는 것이다.

§2지금 브랜치 상태 (2026-06-12 실측)

⚠ 지금 바로 알아야 할 2가지 (실측에서 발견) ① 메인 폴더가 detached HEAD — "Unity Setting"(a0f53fd, Multiplayer Tools 패키지 설치 기록) 커밋이 어느 브랜치에도 속하지 않은 채 떠 있다. 이대로 다른 곳으로 체크아웃하면 이 커밋을 찾기 어려워진다. → §3에서 1분 정리.
② 두 claude 브랜치의 추적(upstream)이 둘 다 origin/feature/pC/namkyu/harness로 잘못 묶여 있다 — SourceTree에서 그냥 Push 버튼을 누르면 넷코드 커밋이 하네스 원격 브랜치로 올라가는 사고가 난다. → §6의 방법대로만 푸시할 것.

§3먼저 1분 정리 — detached HEAD 구하기

메인 폴더에서 아래를 실행한다 (SourceTree 우상단 터미널 버튼 → Git Bash/cmd 열림). "Unity Setting" 커밋에 이름표(브랜치)를 붙여 잃어버리지 않게 만드는 것뿐이다.

# 메인 폴더(pB)에서 — 지금 HEAD(a0f53fd)에 브랜치 이름을 붙인다
git branch chore/unity-packages a0f53fd

이제 메인 폴더는 자유롭게 체크아웃해도 안전하다. 이 커밋(Multiplayer Tools 설치 기록)은 §5 통합 테스트 때 같이 머지하면 된다.

이 커밋의 정체 Unity에서 Multiplayer Tools 패키지를 설치하면서 생긴 manifest.json+packages-lock.json 변경이다. 넷코드 브랜치(Step 0)에도 같은 manifest 한 줄이 들어 있어서, 머지하면 같은 내용으로 합쳐지거나 한 줄짜리 충돌이 난다 — 충돌 시 넷코드 쪽(또는 아무 쪽이나 같은 버전)을 선택하면 된다. packages-lock은 Unity가 다시 만들어 주므로 어느 쪽을 골라도 무방.

§4케이스 A·B — 한쪽 작업만 Unity에서 테스트

핵심 아이디어: Library(임포트 캐시)가 있는 메인 폴더에서 테스트한다. 워크트리 폴더를 Unity로 직접 열 수도 있지만(§8 옵션) 첫 임포트가 매우 오래 걸린다.

단, claude 브랜치들은 워크트리에 물려 있어 메인 폴더에서 같은 이름으로 체크아웃이 안 된다. 그래서 "같은 커밋을 가리키는 테스트용 브랜치"를 만들어 체크아웃한다.

A. 넷코드만 테스트

1
Unity를 닫는다. (브랜치 전환 중 파일이 바뀌면 임포트가 꼬일 수 있음)
2
메인 폴더 터미널에서: 
# test/netcode 라는 이름으로 넷코드 브랜치의 현재 커밋을 체크아웃 (-B = 있으면 갱신)
git checkout -B test/netcode claude/sharp-boyd-9b7050
3
Unity로 메인 폴더를 연다 → 변경된 스크립트만 컴파일된다(수 분 내). 콘솔에 [NetDiag] 세션 출력 폴더: 로그가 보이면 계측 시스템 정상 가동.
4
테스트 후 수정할 게 나오면 → 메인 폴더에서 고치지 말고 넷코드 Claude 채팅에 말한다 (§6의 프롬프트). 수정 커밋이 올라오면 2번을 다시 실행하면 끝.

B. 하네스만 테스트

git checkout -B test/harness claude/laughing-gates-da429a

나머지는 A와 동일. 하네스는 .claude·.harness 폴더 중심이라 Unity 컴파일에는 거의 영향이 없고, Claude Code 동작(훅·스킬)을 확인하는 테스트가 된다.

왜 test/* 브랜치를 따로 만드나? 같은 브랜치를 두 폴더에서 체크아웃하면 git이 거부한다(워크트리의 안전장치). 이름만 다른 브랜치(test/netcode)를 같은 커밋에 붙이면 우회된다. test/* 브랜치에서는 절대 커밋하지 말 것 — 테스트 전용 일회용이며, 매번 -B로 덮어쓴다.

§5케이스 C — 두 작업을 합쳐서 테스트

1
Unity를 닫고, 메인 폴더 터미널에서: 
# master 기준으로 통합 브랜치 생성
git checkout -B test/integration master

# 넷코드 + 하네스 + 패키지설정 커밋을 순서대로 머지
git merge claude/sharp-boyd-9b7050
git merge claude/laughing-gates-da429a
git merge chore/unity-packages
2
충돌이 나면 — 예상 지점은 Packages/manifest.json 한 곳뿐이다. SourceTree 좌측 "파일 상태"에서 충돌 파일 우클릭 → 충돌 해결 → 내것/저것 선택, 또는 그냥 Claude 채팅에 맡긴다(§6 프롬프트 3번).
3
Unity로 메인 폴더 열기 → 통합 상태 테스트. (2인 테스트 절차는 Reports/SCN_Procedures.md)
4
문제가 나오면: 어느 쪽 문제인지에 따라 해당 Claude 채팅에 수정을 시키고, 커밋이 올라오면 1번부터 다시 (머지 다시 하면 됨 — -B가 매번 새로 만들어 준다).

§6케이스 D — GitHub 최종 업로드 (가장 중요)

이 프로젝트의 브랜치 명명 규칙대로, 최종 목적지는 이미 만들어져 있다:

작업로컬 작업 브랜치GitHub 목적지
넷코드claude/sharp-boyd-9b7050feature/pC/namkyu/netcode
하네스claude/laughing-gates-da429afeature/pC/namkyu/harness
⚠ SourceTree의 Push 버튼을 그냥 누르지 말 것 두 claude 브랜치의 추적 설정이 둘 다 origin/feature/pC/namkyu/harness로 잘못 묶여 있어, 기본 Push가 엉뚱한 원격 브랜치로 나간다. 아래의 "로컬브랜치:원격브랜치" 지정 푸시만 사용한다. (한 번 아래 ②의 -u 옵션으로 푸시하면 추적이 올바르게 교정되어 이후엔 버튼 푸시도 안전해진다.)

방법 ① 명령 한 줄 (간단·권장)

# 넷코드 업로드 — 아무 폴더에서나 실행 가능 (워크트리 포함)
git push origin claude/sharp-boyd-9b7050:feature/pC/namkyu/netcode

# 하네스 업로드 (원격 harness 브랜치에 이어 붙이기)
git push origin claude/laughing-gates-da429a:feature/pC/namkyu/harness

콜론(:) 왼쪽=내 로컬 브랜치, 오른쪽=GitHub에 올라갈 브랜치 이름이다. 이후 GitHub에서 PR을 만들어 master로 머지하면 끝.

방법 ② 추적 설정까지 교정하면서 푸시 (이후 버튼 푸시 가능)

# 각 워크트리 폴더의 터미널에서 (또는 Claude 채팅에 시키기)
# 넷코드 워크트리에서:
git push -u origin claude/sharp-boyd-9b7050:feature/pC/namkyu/netcode
# 하네스 워크트리에서:
git push -u origin claude/laughing-gates-da429a:feature/pC/namkyu/harness

방법 ③ SourceTree GUI로만 하고 싶다면

1
상단 Push 클릭 → 푸시할 브랜치 체크박스에서 해당 claude 브랜치 선택
2
"원격 브랜치" 칸을 반드시 직접 수정 — feature/pC/namkyu/netcode(넷코드) 또는 feature/pC/namkyu/harness(하네스)로 타이핑
3
"추적 설정" 체크 후 Push → 이후부터는 버튼 푸시도 올바른 곳으로 나간다
master 반영까지 하려면 GitHub 웹에서 feature/pC/namkyu/netcode → master PR 생성·머지가 정석(협업자 Ethaniya0912와 리뷰 가능). 로컬에서 직접 하려면: git checkout master && git merge feature/pC/namkyu/netcode && git push origin master. 머지 후에는 §9의 프롬프트로 각 워크트리에 "master 최신을 머지해줘"라고 시켜 동기화한다.

§7케이스 E — 수정점이 나왔을 때의 일상 루프

버그를 메인 폴더에서 발견해서 급하게 직접 고쳤다면? test/* 브랜치에 커밋하지 말고, 수정 내용을 복사해 두고 되돌린 후 Claude 채팅에 시키는 게 깔끔하다. 이미 커밋했다면 해당 채팅에 "메인 폴더의 test/netcode 브랜치에 내가 커밋한 ___ 를 이 브랜치로 가져와(cherry-pick)줘" 라고 부탁하면 된다.

§8옵션 — 워크트리 폴더를 Unity로 직접 열기 / SourceTree에 탭 추가

워크트리를 별도 Unity 프로젝트로 열기 (동시 2개 에디터 가능)

워크트리 폴더에도 Assets·Packages·ProjectSettings가 다 있으므로 Unity Hub → Add → pB\.claude\worktrees\sharp-boyd-9b7050 선택으로 열 수 있다. 메인과 워크트리를 동시에 두 에디터로 띄울 수도 있다(폴더가 다르면 Unity가 허용).

장점단점
브랜치 전환 없이 즉시 테스트, 두 작업 나란히 비교 가능첫 임포트가 매우 오래 걸림(Library가 없어 전체 리임포트) + 디스크 수십 GB 추가
첫 임포트 단축 팁 — Unity를 모두 닫은 상태에서 메인 폴더의 Library 폴더를 워크트리 폴더로 복사해 두고 열면 대부분 캐시가 재활용된다(Library는 캐시라 복사해도 안전 — 불일치 부분만 Unity가 다시 굽는다). 그래도 수십 GB 복사라는 점은 감안.

SourceTree에서 워크트리를 별도 탭으로 보기

파일 → 열기(또는 새 탭 +) → 워크트리 폴더 선택. 그 탭에서는 해당 워크트리의 파일 상태·커밋이 보인다. 단 푸시·브랜치 그래프는 메인 탭과 동일한 저장소를 공유하므로, 그래프 확인은 메인 탭 하나로 충분하다.

§9복붙용 Claude 프롬프트 모음

상황어느 채팅에

1. 작업 브랜치를 master 최신과 동기화 (master가 갱신된 뒤 각 채팅에서):

origin에서 fetch 받고 master 최신을 이 브랜치에 머지해줘. 충돌나면 해결 방안 보고하고 진행해.

2. GitHub 업로드 (넷코드 채팅 기준 — 하네스 채팅이면 브랜치명만 교체):

현재 브랜치를 origin의 feature/pC/namkyu/netcode 로 푸시해줘. -u 로 추적도 교정하고, 푸시 전에 어떤 커밋들이 올라가는지 목록 보여줘.

3. 통합 테스트 브랜치 생성/갱신 (아무 채팅이나 — 메인 폴더는 Unity를 닫은 상태에서):

메인 저장소 폴더(D:\남규\프로젝트\Unity\pB)에서 test/integration 브랜치를 master 기준으로 새로 만들고, claude/sharp-boyd-9b7050, claude/laughing-gates-da429a, chore/unity-packages 를 순서대로 머지해줘. 충돌나면 파일별로 어느 쪽을 택했는지 보고해. 단, 머지 전에 메인 폴더에 커밋 안 된 변경이 있는지 먼저 확인해.

4. 테스트에서 발견한 버그 수정 지시 (해당 채팅에):

Unity에서 테스트해보니 [증상: 어떤 씬에서, 어떤 조작 시, 어떤 에러/현상]. 콘솔 에러: [붙여넣기]. 원인 찾아서 수정하고 커밋해줘.

5. 지금 상태 브리핑 (헷갈릴 때 아무 채팅에):

git worktree list 와 git branch -vv, git log --oneline --graph --all -15 결과를 보여주고, 지금 어떤 브랜치가 어디에 체크아웃되어 있고 푸시 안 된 커밋이 뭔지 한국어로 요약해줘.

6. 작업 완전 종료 후 워크트리 정리 (모든 머지·푸시가 끝난 뒤):

이 작업은 master에 머지 완료됐어. 이 워크트리를 안전하게 정리해줘 — 푸시 안 된 커밋이 없는지 먼저 확인하고, 있으면 중단하고 알려줘.

§10FAQ — 초보가 반드시 만나는 에러들

증상의미와 해결
fatal: 'claude/...' is already checked out at ... (SourceTree 체크아웃 에러)그 브랜치는 워크트리가 점유 중이라는 뜻. 정상 동작이다. §4처럼 git checkout -B test/이름 브랜치명 으로 우회한다.
SourceTree Push가 자꾸 harness 원격으로 가려고 함추적 설정 오류(§2 ②). §6 방법 ②의 -u 푸시 한 번이면 영구 교정.
Unity가 갑자기 대량 리임포트 시작에디터가 열린 채 브랜치를 전환했기 때문. 기다리면 되지만, 큰 전환(통합 머지 등)은 Unity를 닫고 하는 습관을 들일 것.
워크트리 폴더를 탐색기에서 그냥 삭제해버렸다커밋된 내용은 .git에 남아 있어 안전하다. 메인 폴더에서 git worktree prune 실행 후, 필요하면 브랜치에서 워크트리를 다시 만든다 — 단 커밋 안 한 변경은 사라지므로 삭제 전 반드시 해당 채팅에 커밋을 시킬 것.
메인 폴더 SourceTree에 "(detached HEAD)" 표시브랜치 없이 커밋 위에 서 있다는 뜻. 그 상태에서 커밋하면 이름표가 없어 나중에 찾기 어렵다. §3처럼 즉시 브랜치를 붙인다.
두 채팅이 같은 파일을 고친다고 한다지금 구조(넷코드=Assets/Scripts, 하네스=.claude)는 겹치지 않지만, 겹칠 작업이라면 한쪽을 먼저 master에 머지하고 다른 쪽에 "master 머지해줘"(§9-1)를 시킨 후 진행하는 것이 충돌을 최소화한다.
packages-lock.json 충돌아무 쪽이나 선택해도 됨 — Unity가 manifest 기준으로 다시 생성한다. 확실하게 하려면 충돌 해결 후 Unity를 한 번 열어 자동 갱신시키고 커밋.
