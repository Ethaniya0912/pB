# unity-pipeline — Unity 개발 자동화 파이프라인

기획 문서를 입력으로 **8단계 SE 분석·명세·테스트 셋업**을 절차적으로 수행하고,
`unity-cli`로 구현 루프를 돌린다. 산출물은 `.harness/cycles/<id>/` 에 누적된다.

## 1. Overview — 무엇을·왜
한 기능/보고 단위(=1 사이클)를 `target→goal→scope→assets→spec→test_env→plan→result`
순서로 분석·셋업하고, 구현 루프로 검증한다. 핵심 원칙은 **결정(Skill)과 강제(Hook)의 분리**:
- 이 스킬은 "무엇을·어떻게"를 안내한다(절차·매트릭스·CLI 템플릿).
- **훅이 게이트를 강제**한다 — 정합화·검증·종료 차단은 LLM 판단과 무관하게 자동으로 일어난다.
  너는 게이트에서 "멈추고 질문"하는 책임만 진다.

## 2. When to use / not
- **사용:** 기획서로 개발 계획 수립, 영향도 분석, 에셋 작업 목록·기술명세 작성,
  테스트 환경 구축, 다중 task 구현 루프 등 **사이클 단위 작업**.
- **비사용:** "이 함수 한 줄 고쳐줘" 같은 단발·1-step 질의. 이때는 그냥 직접 처리한다.

## 3. Preconditions (사이클 시작 전 확인)
1. **사이클 폴더 존재** — `/cycle-start <문서>` 로 스캐폴딩됐는가? 없으면 사용자에게 `/cycle-start`
   실행을 안내한다(이 스킬은 폴더를 직접 만들지 않는다 → 부작용은 cycle-start 전용).
2. **Unity ready** — `unity-cli status` 가 `ready` 인지 확인. busy 면 unity-cli 가 대기하므로
   그대로 진행 가능. 무응답이면 "Editor offline"으로 보고 후, 분석 단계(①~⑤)는 계속하되 실행
   단계(⑥ 이후)는 사용자에게 Editor 기동을 요청한다.
3. **컨텍스트 로드** — `.harness/_conventions.md`, 최신 `snapshots/`, 이전 사이클 `04_assets.md` 를
   필요 시 참조한다(③ scope 에서 핵심).

## 4. 9단계 절차
각 단계는 **입력 → 활동 → 산출물 → 게이트 → CLI**. 상세 지침은 `references/stage-0N-*.md`,
매트릭스 컬럼은 `references/matrix-schemas.md`, CLI 스니펫은 `references/cli-cookbook.md`.
산출물은 `assets/templates/` 의 빈 템플릿을 복사해 채운다.

> 진행 규약: 각 단계 완료 시 해당 `0N_*.md` 를 작성하고, `meta.json` 의 `status`/`awaiting_gate`
> 를 갱신한다. 게이트가 걸린 단계는 **멈추고 사용자 확인**을 받은 뒤 다음 단계로 간다.
> **모든 단계 문서는 매트릭스(정밀)+Mermaid(관계 시각화)를 함께** 쓰고, 강화된 "이 문서는?"(5W1H)으로
> 시작하며, 참조되는 ID(T·G·A·게이트)에 앵커를 단다(_conventions §13·§14-A·§7-A — 템플릿 내장).

### ① target — 기획 내용 정리  ▸ `01_target.md`  ▸ **G1**
- 입력: `00_input/` 의 기획·구현·기술개론 문서.
- 활동: 순수 기획 내용을 **빈틈 없이 리스트화·분류**한다(해석/추론과 원문을 구분).
  as-is 스냅샷(`snapshots/`)을 확보한다.
- 산출물: target 매트릭스(ID·항목·분류·원문근거·해석·모호도).
- **G1 게이트**: 모호·누락 항목과 SE 해석을 사용자에게 확인받는다. → 상세 `references/stage-01-target.md`

### ② goal — 개발 요구사항 도출  ▸ `02_goal.md`
- 활동: 각 target → 개발 요구사항으로 변환·**매핑**. 요구사항별 필요 시스템·에셋 범주 분류.
- 산출물: goal 매트릭스(Goal-ID·연결 target·요구사항·시스템·에셋범주·우선순위).

### ③ scope — 변경 범위·영향도  ▸ `03_scope.md`  ▸ **G2**
- 활동: 각 요구사항이 **기구현/신규**인지 판정하고 영향도를 분석한다. `unity-cli exec` 로
  타입·에셋 존재를 확인하고, **이전 사이클 `04_assets.md` 와 최신 `snapshots/` 를 조회**해 중복을 피한다.
- **위임 기본**: 존재성 스캔은 **`asset-auditor` 서브에이전트**(read-only)가 기본 수행(§8).
  질의가 3건 이하일 때만 메인이 직접 한다.
- 산출물: scope 매트릭스 + **변경 범위 Mermaid**(as-is/to-be subgraph, 기구현=회색·신규=초록·수정=골드).
- CLI: `unity-cli exec "System.Type.GetType(\"Game.Inventory\")!=null"` (쿡북 §존재확인)
- **G2 게이트**: 기존 에셋 수정·영향도 높은 항목을 승인받는다.

### ④ assets — 에셋 작업 목록 확정  ▸ `04_assets.md`  ▸ **G3**
- 활동: 변경·신규 에셋을 범주별로 리스트화하고 **실제 파일·경로명을 확정**해 goal 과 매핑.
- 산출물: assets 매트릭스 + **변경·활용 맵 Mermaid** + **Hierarchy 배치 표**(§15 — 씬 경로 또는 "런타임 자동생성" 명시).
- **G3 게이트**: 실제 생성 전에 네이밍·경로를 확정받는다(이후 파일명이 계약이 됨).

### ⑤ spec — 기술 명세서  ▸ `05_spec/<A-ID>_<에셋명>.md`
- 활동: 각 에셋의 기술명세 작성. 스크립트는 **클래스·책임·인터페이스·의존성·공개 API**,
  그 외(prefab/scene/asset/mat)는 **사양·포맷·제약·참조 관계**.
- **쉬운 설명 섹션 필수** — 기술 명세 앞에 비개발자용 "무엇·왜" 1~3문장(§6.1-4).
- **산출물 사용 가이드 섹션 필수**(§16) — 기술 명세 뒤에 언제·왜 만듦 / Unity 적용법 / 사용법 / 주의점.
- **위임 기본**: 에셋 3건 이상이면 **`spec-writer` 서브에이전트**에 에셋별 병렬 위임(§8) — 메인은 검수·교차 정합만.
- 산출물: `05_spec/` 하위 에셋 단위 파일. 템플릿 `assets/templates/05_spec_asset.md`.

### ⑥ test_env — 테스트 환경 정의  ▸ `06_test_env.md`  ▸ **G5**
- 활동: 프로젝트 구조·오브젝트·프리팹·씬을 **as-is / to-be** 로, unity-cli 가 실행 가능한
  수준으로 기술한다. 텍스트 편집 후 `reserialize` 로 정합화(**PostToolUse 훅이 자동 수행**).
- **to-be Hierarchy 배치 트리 필수**(§15) — 오브젝트가 씬 계층 어디에 들어가나(레이어 `━━━━`→그룹 `───`→GO).
  **런타임 자동생성이면 "씬 배치 없음 — 자동생성"임을 명시**(사람이 씬을 헛되이 뒤지지 않게).
- CLI: 씬/프리팹 셋업 스니펫은 쿡북 §씬셋업. 편집은 Edit/Write 로 → 훅이 reserialize+compile.
- **G5 게이트**: as-is→to-be 실제 적용 전에 승인받는다.

### ⑦ plan — 체크리스트·진행관리  ▸ `07_plan.md`
- 활동: 전 과정 task 를 세분화한 **체크리스트**(`- [ ]`)를 만든다. 구현 루프의 작업 큐가 된다.
- 규약: 미완료 `- [ ]` / 완료 `- [x]`. **Stop 훅이 미체크 개수로 사이클 미완료를 판정**한다.

### ⑧ result — 결과 보고서  ▸ `08_result.md`  ▸ **G7**
- 활동: ①~⑦ 완료 시 결과 종합 + as-is→to-be 변화를 **스냅샷 diff** 로 첨부.
- **검증 증빙 필수**(§6.1-5): 검증 일시·환경, task별 검증 기록, 콘솔 발췌, 스크린샷·산출물
  실링크를 `evidence/` 기반으로 첨부. 용어 사전 갱신 내역도 명시.
- **다측면 이점 섹션 필수**: 이번 사이클이 가져온 가치를 게임·개발·기획·아트·운영 측면으로 정리(_conventions §14).
- **산출물 인수인계 표 필수**(§16): 산출물별 무엇·적용(자동/수동)·사용법·주의를 한눈에.
- **G7 게이트**: 보고서·diff·증빙·이점·인수인계 검토 후 사인오프. `meta.json.status="signed_off"`, `_index.md` 에 완료 기록.

### ⑨ next — 다음 사이클 이관  ▸ `09_next.md`  ▸ **G8**
- 활동: 잔여 task·후속 제안·측정 대기를 **차기 사이클 후보**로 승격하고, 이관 흐름을 Mermaid 로 그린다.
  result 의 "잔여 이슈"를 실행 가능한 입력으로 구조화한다(없으면 "이관 없음" 명시).
- 산출물: 차기 후보 매트릭스 + 이관 Mermaid + 권장 다음 사이클(slug·입력·선행조건).
- **G8 게이트(질의)**: 문서 끝에서 **자동 진행을 멈추고** "이번 사이클 종료 — 다음 사이클을 바로 시작할까요?"를
  사용자에게 묻는다. 예 → 권장 입력으로 `/cycle-start` 안내·실행 / 아니오 → 인계장 보관 후 종료.

## 5. 게이트 규약 (R2 · 휴먼-인-더-루프)
- **행동 규칙:** 게이트(G1·G2·G3·G5·G7·G8)에 도달하면 **자동 진행을 멈추고** 결정 요약과
  선택지를 제시한 뒤 사용자 응답을 기다린다. 모호하거나 비복구 변경이면 임의 진행 금지.
- **기록:** 모든 게이트 결정은 `decisions.md` 에 `## <a id="G2"></a>G2 (2026-06-11) — 승인 ...` 형식(헤더 앵커 포함)으로 남긴다.
  awaiting_gate 가 걸린 채 종료하면 **Stop 훅이 decisions.md 기록을 요구**한다.
- **G4(파괴적 CLI)** 는 PreToolUse 훅이 자동으로 ask/deny → 사용자가 권한 프롬프트로 응답.
- **G6(설계 분기)** 는 테스트 실패가 기계적 수정이 아닐 때 선택지를 제시(수동).
- **G8(다음 사이클 진행)** 은 ⑨ next 끝에서 다음 사이클 즉시 진행 여부를 질의(수동).
- 게이트별 질문 양식·결정 트리·기록 형식은 `references/gates.md`.

## 6. 산출물·누적 규약 (R4)
- 경로: `.harness/cycles/<YYYY-MM-DD_slug>/`, 단계 파일 `01~09` 넘버링(상세 `_conventions.md`).
  스펙은 `05_spec/<A-ID>_<에셋명>.md`, 증빙은 `evidence/`, 용어 사전은 `.harness/glossary/`.
- 갱신: 각 단계가 `0N_*.md` 작성 → `meta.json` 상태 갱신 → 완료 시 `_index.md` append.
- **재사용(누적의 핵심):** ③ scope 에서 이전 사이클 `04_assets.md` 와 `snapshots/` 를 조회해
  "이미 구현됨"을 판단 → 중복 분석 방지·영향도 정확도 향상.
- 보관: 완료 사이클은 `archive/` 로, `_index.md` 에 포인터 유지.

### 6.1 문서 작성 규약 — Foam 지식 그래프 (모든 단계 공통, `_conventions.md` §7~§11)
모든 산출물 md 는 VS Code **Foam** 으로 탐색 가능한 지식 그래프의 노드다. 작성 시:
1. **상호 링크** — 문서 끝 `## 🔗 관련 문서 (Foam)` 블록(템플릿 내장)을 채운다.
   md↔md 는 위키링크(`[[<cycle-id>/03_scope|③ scope]]`), 섹션 연결은 `[[파일#헤딩|표시]]`.
2. **용어 사전 누적** — 산출물에 새 용어(개념/도구/스크립트/에셋/패키지)가 등장하면
   `glossary/<분류>/<용어>.md` 를 등록·갱신하고(템플릿 `glossary/_template.md`),
   `_glossary.md` 인덱스에 한 줄 추가, 본문 **첫 등장에 `[[용어]]` 링크**, 사전의
   "등장 사이클" 섹션에 **역링크**를 남긴다. 재등장 용어는 역링크 줄만 추가(누적).
3. **실제 에셋 링크** — 에셋·산출물 경로는 클릭으로 열리는 상대경로 링크
   `` [`Assets/...`](../../../Assets/...) `` 로 적는다(04_assets·08_result·spec 메타 필수).
4. **비개발자 가독성** — 각 문서 도입부 "이 문서는?" 1~2문장(템플릿 내장), 어려운 용어는
   첫 등장에서 괄호 풀이 또는 사전 링크, 표 밖 평문으로 흐름 설명.
5. **검증 증빙** — "검증 완료" 주장에는 근거를 첨부한다: 검증 일시·환경(`status` 출력)·
   task별 기록·콘솔 발췌·스크린샷을 `evidence/` 에 저장하고 08_result 증빙 섹션에 연결.
   수집 명령은 쿡북 §8. ⑦ plan 의 "마감 정리" task 가 이를 체크리스트로 강제한다.
6. **Mermaid 시각화** — 단계별 권장 다이어그램(_conventions §13-A)을 매트릭스와 함께 둔다.
   의미색 5종 표준(추가=초록·수정=골드·삭제=빨강·유지=회색·흐름=파랑, §13-B), 노드 라벨에 매트릭스 ID 포함.
7. **ID 앵커** — 참조되는 T·G·A·게이트 ID 에 `<a id>` 앵커를 달고, 가리키는 쪽은 `[T1](01_target.md#T1)`
   로 점프(§7-A). 원문근거는 입력 문서로 링크.
8. **강화 "이 문서는?"** — 도입부에 왜·무엇·어떻게·언제·누가를 녹여 목적을 구체화(§14-A).
9. **Hierarchy 배치**(④⑥) — 오브젝트가 씬 계층 어디에 들어가나(레이어 `━━━━`→그룹 `───`→GO). **자동생성이면
   "씬 배치 없음 — 런타임 자동생성"임을 명시**(§15). ⑥ 은 to-be Hierarchy 트리.
10. **산출물 사용 가이드**(⑤⑧) — ⑤ spec 에 언제·왜 만듦 / Unity 적용법 / 사용법 / 주의점, ⑧ result 에
    산출물 인수인계 표. 코드 모르는 팀원도 "켜고·쓰고·주의"를 알게(§16).

## 7. 구현 루프 (⑦ 이후, task 단위 반복)
각 task 에 대해:
1. **편집** — Edit/Write 로 스크립트·에셋 텍스트 수정.
2. **정합화·컴파일** — Unity YAML 에셋(`.prefab/.unity/.asset/.mat/.anim/.controller` 등)은
   **PostToolUse 훅이 자동으로** `reserialize → editor refresh --compile → console --type error`
   수행. 코드 계열(`.cs/.asmdef/.shader` 등)은 compile 만.
   → **너는 reserialize 를 수동 호출하지 않는다**(훅 책임). 훅이 stderr 로 에러를 돌려주면 수정한다.
3. **콘솔 확인** — 컴파일 에러 없으면 다음으로. 있으면 수정 후 재편집(루프 재진입).
4. **플레이 테스트** — `unity-cli editor play --wait` 로 진입 → 동작 확인 → `console` 재확인 → 판정.
   **위임 기본**: play 판정은 `test-runner` 가 수행하고 증빙(콘솔 덤프·스크린샷)을 evidence/ 에
   저장해 돌아온다(§8) — 메인이 직접 play 를 돌리는 것은 예외.
5. **판정** — 통과 시 `07_plan.md` 의 해당 task 를 `- [x]` 로 체크 → 다음 task.
   실패 시 수정 후 루프 재진입. 설계 결정이 필요한 실패는 **G6** 로 사용자에게 질문.
- 모든 task 완료 → 마감 정리(용어 사전·증빙·**최종 스모크**) → ⑧ result → ⑨ next(이관·G8 질의).

## 8. 서브에이전트 — 기본 위임 정책 (응답시간·컨텍스트의 핵심)
**원칙: 격리 가능한 작업은 위임이 기본값, 메인 직접 수행이 예외다.** 메인 컨텍스트는
분석·게이트 판단·검수에만 쓴다. 독립 작업은 **한 메시지에 묶어 병렬로** 위임한다.

| 단계·상황 | 에이전트 | 기본/예외 | 반환물 |
|---|---|---|---|
| ③ scope 존재성 스캔 | `asset-auditor` | **기본** (질의 ≤3건일 때만 메인 직접) | scope 매트릭스 초안 + 사전 등록 후보 |
| ⑤ spec 작성 | `spec-writer` | **기본** (에셋 3건 이상 — 에셋별 병렬 호출; 1~2건은 메인) | spec md 파일 작성 + 확인 필요 지점 |
| 구현 루프 검증(play/console) | `test-runner` | **기본** (compile-only 단건은 훅 결과로 충분) | PASS/FAIL + **evidence/ 증빙 경로** |
| 사인오프 직전 최종 스모크 | `test-runner` | **필수** (⑦ 마감 정리 task) | 〃 |
- 위임 시 프롬프트에 반드시 포함: 사이클 경로·cycle-id, 무관 기존 에러 패턴, 기대 반환 형식.
- 에이전트 반환물은 검수 후 산출물에 그대로 옮긴다(재작성 금지 — 중복 작업이 응답시간 주범).

### 8.1 성능 원칙 (응답시간 단축)
1. **배치 exec** — 존재 확인·상태 질의 여러 건은 exec 1회에 묶는다(쿡북 §2 배치 예시).
2. **대용량 출력은 파일 경유** — 콘솔 덤프·스냅샷·컴포넌트 목록은 stdout 으로 받지 말고
   파일로 쓰게 한다(`> evidence/...txt`, exec 내 `File.WriteAllText`). 대화에는 발췌만(쿡북 §9).
3. **병렬 위임** — 독립 에이전트 호출(예: spec-writer 에셋별)은 같은 메시지에 묶는다.
4. **게이트 질문은 묶어서 1회** — 같은 게이트의 결정 사항을 쪼개 여러 번 묻지 않는다(gates.md 트리).
5. **재조회 금지** — 에이전트가 이미 읽은 파일 목록을 반환하므로 메인이 다시 읽지 않는다.
