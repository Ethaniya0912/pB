# ③ scope — 변경 범위·영향도 (상세)

목적: 각 요구사항이 **기구현/신규/변경**인지 판정하고 영향도를 분석한다. (누적 재사용의 핵심 단계)

## 입력
- `02_goal.md` goal 매트릭스 · 최신 `snapshots/` · **이전 사이클들의 `04_assets.md`**.

## 활동 체크포인트
1. 각 goal 의 대상 타입/에셋이 **이미 존재하는지** `unity-cli exec` 로 확인한다.
   - 쿡북 §2 존재 확인(타입/에셋/오브젝트).
2. **이전 사이클 `04_assets.md`** 를 조회해 "이미 만든 것"을 식별 → 중복 구현 방지.
3. 신규/기구현/변경으로 상태를 분류하고, 변경 시 **영향 범위**(참조 씬·프리팹·시스템)를 적는다.
4. 리스크를 평가(낮음/보통/높음). 기존 에셋 변경·고영향은 G2 승인 대상.

## 위임 (기본값 — SKILL §8)
- 존재성 스캔은 **`asset-auditor`** 서브에이전트가 기본 수행한다(read-only, 코드 수정 금지).
  질의가 3건 이하일 때만 메인이 직접 한다(배치 exec — 쿡북 §2).
- 반환물: scope 매트릭스 초안 + 사전 등록 후보 + 참조 파일 목록. 본 단계(메인)는
  **검토·영향도/리스크 확정·G2 질문**만 담당한다. 에이전트가 읽은 파일을 다시 읽지 않는다.

## 산출물 — scope 매트릭스 + 변경 범위 Mermaid
컬럼: `연결 goal | 상태 | 대상 에셋·타입 | 존재 근거 | 영향 범위 | 리스크`

**변경 범위 Mermaid 필수**(_conventions §13): `flowchart` + `as-is`/`to-be` subgraph 로 이번 사이클이
**접근·수정하는 범위만** 그린다. 기구현=회색(keep)·신규=초록(add)·수정=골드(mod), 영향 화살표는 점선.
"연결 goal" 열은 `[G1](02_goal.md#G1)` 로 ②에 점프(§7-A).

예시:
| 연결 goal | 상태 | 대상 에셋·타입 | 존재 근거 | 영향 범위 | 리스크 |
|---|---|---|---|---|---|
| G1 | 신규 | Game.Inventory.* | exec=false | 신규 씬 | 낮음 |
| — | 변경 | PlayerController | exec=true | Player.prefab, Main.unity | 높음 |

## G2 게이트 (Stop 강제)
- 기존 에셋 수정·영향도 높은 항목을 승인받는다. 양식·기록: `references/gates.md`.
- 통과 후 `meta.json.status` 유지(planning), `awaiting_gate` 해제.

## 흔한 실수
- 이전 사이클 미조회로 중복 구현.
- 영향 범위를 "코드"만 보고 판단(씬/프리팹 참조 누락).
