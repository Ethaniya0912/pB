# 위키 규약 — pB 실체 반영 + 비판 + 유지보수

> 이 위키는 "기획 사전준비 뼈대"에서 **pB 실제 구현을 반영한 살아있는 지식베이스**로 전환됐다.
> 단순 문서화가 아니라 **현황 + 설계 결정 + 비판(약점·부채·리스크)** 을 함께 담는다.

## 1. 문서 형식
- **frontmatter**: `title`(한글) · `tags` · `status` · `source`(근거 코드/문서 경로 배열) · `verified`(YYYY-MM-DD).
- **본문 구조**:
  1. 제목 + 한 줄 요약
  2. `## 현황 (pB)` — 실제 구현 상태. **코드 경로를 인용**(`Assets/Scripts/...`). 미구현이면 "미구현"으로 솔직히.
  3. `## 설계·결정` — 어떤 선택을 왜 했나(ADR 문서는 맥락/선택지/결정/근거/영향).
  4. `## ⚠ 비판·리스크` (**필수**) — 현 설계의 약점·기술부채·확장성 한계·검증 안 된 가정.
     입에 발린 말 금지. 구체적 근거(코드/수치)와 함께. 심각도(높음/보통/낮음) 표기 권장.
  5. `## 관련 문서` — 위키링크 `[[slug|한글]]`.
  6. 푸터 — `← [[<hub>|상위]] · [[index|인덱스]]`.
- **네이밍**: 파일명·폴더는 영문(ASCII). 제목·표시는 한글(frontmatter `title`, 위키링크 별칭).

## 2. status 값
`todo`(빈 스텁) · `researching`(조사 중·부분) · `decided`(결정됨·미구현) · `done`(현황 반영 완료).
- 기획 정보(장르·코어루프·타겟 등 코드로 알 수 없는 것)는 추정 초안 + `status: researching` + "확인 필요" 명시.

## 3. 유지보수 — 신선도 (별도 하네스 대신 경량 통합)
풀 하네스(9단계)는 만들지 않는다. 위키는 파이프라인이 아니라 참조물이므로 **신선도 유지**만 한다.
- **source/verified**: 문서가 근거한 코드 경로(`source`)와 검증일(`verified`)을 frontmatter에 남긴다.
- **stale 감지**: `source` 코드가 `verified` 이후 변경됐는지 점검(`.harness/hooks/check-wiki-stale.sh`, 선택).
  변경됐으면 "갱신 필요" 경고 → 해당 문서를 다시 확인·갱신하고 `verified` 갱신.
- **사이클 연결**: `unity-pipeline` 사이클 ⑧ result/⑨ next 마감에서 "이번 변경이 영향 준 위키 문서"를
  갱신한다(영향 없으면 "없음"). 사이클 용어 사전([`.harness/glossary/_glossary.md`](../../.harness/glossary/_glossary.md))의
  용어와 위키 문서는 상호 참조한다(위키는 별도 Foam 워크스페이스라 하네스 사전과는 상대경로 링크로 연결).
- **갱신 단위**: 코드 1줄마다가 아니라 "설계가 바뀌었을 때"(권위 모델·transport·빌드 방식 등). ADR은 새 번호로 추가(기존 ADR 수정 금지, append).

## 4. 비판의 기준 (이 위키의 차별점)
- "잘 됨" 류 금지. **무엇이 부족한지·언제 깨지는지·무엇을 안 했는지**를 적는다.
- 미검증 가정 표시(예: "2인 측정 미집행 — 실측 없음").
- 부채에 우선순위(이 부채가 EA/출시에 언제 터지나).
- 비판은 비난이 아니라 **다음 결정의 입력** — 가능하면 권고(다음 단계)를 붙인다.
