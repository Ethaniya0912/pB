pB · game-dev-wiki

결정 레이어 — 기획 ↔ 개발 브리지 가이드

기획서와 코드 사이에서 "이건 기획 결정이자 동시에 기술 약속"인 경계 결정을 영속적으로 박제하는 문서·도표 체계. pB는 멀티플레이 + 시뮬레이션(팩션·신뢰·트라우마)이라 거의 모든 기획 결정이 권위·동기화·튜닝과 직결됩니다.

제안 (proposed) — 아직 채택 전 초안. 채택 시 13-decisions/ 섹션으로 정식 편입.

01 레이어 지도

기획(의도)과 개발(현실) 사이에 결정 레이어가 들어가, 둘을 잇는다. 가운데가 지금 비어 있는 칸이다.

🎨 기획 (의도)
코어루프 · 장르 · 동접 · 내러티브 — 00-overview/project-overview
↓
🌉 결정 레이어 — 기획 ↔ 개발 경계 (신설)
ADR 기술 결정
기술 선택·트레이드오프 (기존)
예: NGO + Steam P2P · URP + SSGI
GDR 기획 결정
게임 디자인 결정 + 근거 (신설)
예: 사망 = 루트 드롭? · 동접 5인?
FSB 기능·시스템 브리지

예: 채굴 동기화 · 신뢰 시스템
↓
⚙️ 개발 (현실)
as-built 현황 + 비판 · 이슈 레지스터(12-issues) · 코드 / 하네스 사이클
이슈 레지스터의 ⚠ 비판·리스크 항목이 거꾸로 새 결정을 촉발한다(개발 → 결정 레이어 피드백). 즉 양방향이다.

02 용어 설명

용어뜻
결정 레이어기획과 개발 사이에서 경계 결정을 모으는 위키 섹션(13-decisions/). 이 가이드가 설명하는 대상.
ADRArchitecture Decision Record — 기술 결정 기록. 형식: 맥락 / 검토한 선택지 / 결정 / 근거 / 영향. pB에 이미 존재(02-architecture/adr-0001-netcode 등).
GDRGame Design Decision Record — 게임 기획 결정 기록. ADR과 같은 형식에 기술·네트워크 영향 섹션을 더한 것. (신설)
FSBFeature / System Bridge — 기능·시스템 브리지 문서. 한 기능을 기획 의도 → 시스템 → 데이터 → 네트워크 → 검증으로 세로 관통해 기획서와 코드를 한 문서로 잇는다. 결정 레이어의 핵심 산출물. (신설)
3렌즈모든 GDR·FSB의 의무 섹션 3개 — ① 네트워크·권위·동기화 ② 데이터·튜닝 ③ 검증. "기획 결정"을 "기술 약속"으로 번역하는 장치.
M-지표프로젝트의 정량 측정 지표(M1~M11). 예: M5 판정 일치율, M6 대역폭. 검증 렌즈에서 "이 수치로 됐다고 판정"에 인용.
SCN테스트 시나리오(SCN-01~07). 예: SCN-06 AI 20기 부하. 검증 렌즈에서 인용.
P-codeNetcode 실행계획의 작업 코드(예: P0-3 방어/패링 권위, P2-6 재접속). 결정 → 작업 추적 연결 고리.
status결정의 수명 상태: proposed → accepted → implemented → superseded.
append-only결정은 수정하지 않는다. 바뀌면 옛 결정을 superseded로 표시하고 새 ID로 추가. (ADR 규약과 동일)
as-built / 현황코드 실측 기반 현재 구현. 위키 토픽 문서의 ## 현황 (pB). 결정 레이어가 "왜·무엇을 정했나"라면, 현황은 "지금 실제로 어떻게 돼 있나".
⚠ 비판·리스크위키 토픽 문서 의무 섹션. 약점·부채·미검증 가정. 12-issues 레지스터(R-001~)로 집계됨.
하네스 사이클.harness의 8단계 작업 파이프라인(target→goal→scope→assets→spec→test_env→plan→result). 휘발성(작업 단위). 경계 결정이 나오면 GDR/FSB로 승격해 영속화.
권위 (authority)네트워크에서 특정 상태를 누가 쓰는가(Owner-write / Server-write). pB 권한 모델은 03-network/authority-model 참조.

03 결정 흐름

① 어떤 기록을 만드나 (분기)

이 결정은…만들 기록
순수 기술 선택인가? (엔진·라이브러리·아키텍처)ADR  02-architecture
게임 디자인 선택인가? (규칙·진행·밸런스·내러티브)GDR  + 기술·네트워크 영향 필수
한 기능/시스템을 기획→코드로 관통해야 하나?FSB  기능 해부 문서
작은 결정이라 전체 기록은 과한가?결정 로그 한 줄 (선택) → 커지면 위로 승격

② 수명 (lifecycle)

proposed 초안→ accepted 합의→ implemented 현황 링크→ superseded 대체됨

implemented가 되면 해당 결정 문서는 as-built 현황 문서로 링크를 건다(이 결정이 코드의 어디로 실현됐는지). 대체될 땐 옛 문서를 지우지 않고 superseded 표시 + 새 결정 링크.

③ 연결 (양방향 링크)

  • GDR/FSB → 관련 as-built 현황([[authority-model]] 등) + 이슈 R-ID([[risk-register]]) + 근거 ADR
  • 현황 문서 → "이 설계의 근거 결정" 으로 GDR/FSB 역링크
  • 하네스 사이클 ⑦plan·⑧result 에서 경계 결정이 나오면 GDR/FSB로 승격(휘발 → 영속)

④ 무엇이 새 결정을 촉발하나 (trigger)

새 기획 의도
→
이슈 레지스터 ⚠ 항목
→
사이클 중 발견
→
GDR / FSB 작성

05 pB 의무 3렌즈

모든 GDR·FSB가 반드시 답해야 하는 3가지. 위키 토픽 문서에서 ## ⚠ 비판·리스크가 의무인 것과 같은 원리 — 빠지면 나중에 이슈 레지스터에 ⚠로 반드시 되돌아온다.

🔗 네트워크 · 권위 · 동기화
누가 권위(Owner/Server)? 동기화 방식? 대역폭? 난입·재접속 시 동작?
📊 데이터 · 튜닝
어떤 ScriptableObject·수치를 쓰나? itemID·밸런스 → 데이터 파이프라인 연결.
✅ 검증
어떤 M-지표 / SCN 시나리오 / 수용기준으로 "됐다"를 판정하나?

FSB는 한 기능을 세로로 관통한다

기획 의도

시스템
→
데이터 (SO)
→
