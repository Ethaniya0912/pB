pB · game-dev-wiki

결정 레이어 — 기획 ↔ 개발 브리지 가이드

기획서와 코드 사이에서 "이건 기획 결정이자 동시에 기술 약속"인 경계 결정을 영속적으로 박제하는 문서·도표 체계. pB는 멀티플레이 + 시뮬레이션(팩션·신뢰·트라우마)이라 거의 모든 기획 결정이 권위·동기화·튜닝과 직결됩니다.

제안 (proposed) — 아직 채택 전 초안. 채택 시 13-decisions/ 섹션으로 정식 편입.

01 레이어 지도

기획(의도)과 개발(현실) 사이에 결정 레이어가 들어가, 둘을 잇는다. 가운데가 지금 비어 있는 칸이다.

↓
🌉 결정 레이어 — 기획 ↔ 개발 경계 (신설)
ADR 기술 결정
기술 선택·트레이드오프 (기존)
예: NGO + Steam P2P · URP + SSGI
GDR 기획 결정

예: 채굴 동기화 · 신뢰 시스템

⚙️ 개발 (현실)
as-built 현황 + 비판 · 이슈 레지스터(12-issues) · 코드 / 하네스 사이클
이슈 레지스터의 ⚠ 비판·리스크 항목이 거꾸로 새 결정을 촉발한다(개발 → 결정 레이어 피드백). 즉 양방향이다.

02 용어 설명

용어뜻
결정 레이어기획과 개발 사이에서 경계 결정을 모으는 위키 섹션(13-decisions/). 이 가이드가 설명하는 대상.
후보 / 백로그기획서에서 뽑은 결정거리 한 줄(주장·요구·선택지). 싸다. 대부분 여기서 살고 죽는다. 채택된 소수만 결정으로 승격.
트리아지후보를 채택/기각/중복/충돌/보류/분할로 분류·솎아내는 작업. 채택/비채택 판정.
승격 기준후보 → 결정 기록으로 올릴지 거르는 3관문: ① 대안이 있었나 ② 영향이 큰가 ③ 안정적인가. 셋 다 yes일 때만 기록.
ADRArchitecture Decision Record — 기술 결정. 맥락 / 선택지 / 결정 / 근거 / 영향. 기존(02-architecture).
GDRGame Design Decision Record — 게임 기획 결정. ADR 형식 + 기술·네트워크 영향. (신설)
FSBFeature / System Bridge — 기능·시스템 브리지. 한 기능을 기획→시스템→데이터→네트워크→검증으로 세로 관통. (신설)
3렌즈모든 GDR·FSB 의무 섹션 — ① 네트워크·권위·동기화 ② 데이터·튜닝 ③ 검증.
출처 레지스트리기획 doc 목록. 소스ID · 버전/날짜 · 상태(active/superseded) · 파생 항목 수. 후보·결정은 source@버전을 인용.
충돌 로그기획 자료끼리 모순될 때 등록하는 1급 항목. 해소 = 결정(GDR/ADR)이 어느 쪽을 채택할지 판정.
stale인용한 소스가 갱신·폐기되어 재검토가 필요한 상태. 스테일 스윕으로 자동 색출(기존 source/verified 메커니즘 재사용).
M-지표정량 측정 지표(M1~M11). 예: M5 판정 일치율, M6 대역폭. 검증 렌즈에서 인용.
SCN테스트 시나리오(SCN-01~07). 예: SCN-06 AI 20기 부하.
P-codeNetcode 실행계획 작업 코드(예: P0-3, P2-6). 결정 → 작업 추적.
status결정 수명: proposed → accepted → implemented → superseded.
append-only결정은 수정 금지. 바뀌면 옛 결정을 superseded로 두고 새 ID로 추가.
하네스 사이클.harness의 8단계 작업 파이프라인. scope 단계가 인테이크 자리, result에서 결정 승격.

03 결정 흐름

① 어떤 기록을 만드나 (분기)

이 결정은…만들 기록
순수 기술 선택인가? (엔진·라이브러리·아키텍처)ADR
게임 디자인 선택인가? (규칙·진행·밸런스·내러티브)GDR + 기술·네트워크 영향 필수
한 기능/시스템을 기획→코드로 관통해야 하나?FSB
작은 결정이라 전체 기록은 과한가?백로그 요구사항으로만 → 커지면 승격

② 수명 (lifecycle)

proposed→ accepted→ implemented · 현황 링크→ superseded

implemented이면 결정 문서가 as-built 현황으로 링크. 대체 시 옛 문서는 지우지 않고 superseded + 새 결정 링크(append-only).

04 기획서 → 결정: 인테이크 깔때기

기획서 하나에서 후보가 수십~수백 개 나오는 건 정상이다. 문제는 그걸 전부 GDR/FSB/ADR로 만들 때다. 핵심은 깔때기 — 후보는 싸게 받아 두고, 트리아지와 승격 기준으로 걸러, 극소수만 결정 기록으로 올린다.

기획 자료 (소스) · doc@ver — 주장 · 요구 수백
↓ 후보 추출 (한 줄씩)
후보 백로그 — 싸다, 대부분 여기서 정리
↓ 트리아지 — 기각 · 중복 · 충돌 · 보류 솎아냄
채택 (accepted)
↓ 승격 기준 (대안 · 영향 · 안정) — 사소건은 요구사항만
결정 기록 · GDR / FSB / ADR — 수십
비용 비대칭이 핵심. 후보 = 한 줄(싸다) / 결정 = 문서(비싸다). 그래서 승격하기 전에 거른다. 폭발은 백로그에서 흡수된다.

05 트리아지 — 채택 · 비채택 솎아내기

후보 하나하나가 거치는 분류. 이게 당신이 말한 "솎아내는 작업".

기획 doc
@ver
→
후보 추출
백로그 inbox
→
트리아지
분류·판정

트리아지 결과 6갈래:

채택 accepted
유효·필요 → 승격 심사로
기각 rejected
범위 밖·불필요. 이유 한 줄 남김
중복 duplicate
기존 항목에 병합 (216→133 사례)
충돌 conflict
다른 자료와 모순 → 충돌 로그로
보류 hold
선행 결정 대기 → 나중 재검토
분할 split
너무 큼 → 작은 후보 여러 개로

채택된 후보의 두 갈래:

요구사항 only
사소·자명 → 백로그 요구로만 추적. 문서 안 만듦.
승격 → GDR / FSB / ADR
승격 기준 3관문 통과분만 정식 결정 기록으로.
충돌·stale 루프: 충돌 항목은 결정이 판정하면 다시 채택/기각으로 흘러간다. 소스가 바뀌면 승격·요구 항목이 stale로 표시되어 트리아지로 되돌아온다(아래 6장).

06 충돌 · outdated 솎아내기

충돌은 버그가 아니라 "결정 트리거"

두 기획 자료가 모순되면 → 충돌 로그에 등록(아직 무엇이 맞는지 미정) → 결정(GDR/ADR)이 판정한다. 충돌은 결정을 강제하는 신호다.

outdated — 출처·버전·스테일 스윕

기획 doc이 갱신·폐기되면, 그 소스에서 나온 항목을 자동 색출해 재검토한다. 기존 source/verified + check-wiki-stale.sh 메커니즘을 그대로 확장.
